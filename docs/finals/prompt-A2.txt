## Goal

No person on a plant floor says "regime". Everywhere a person reads or hears Thor, the word
becomes **"state"**: "State: heavy load", "the motor changed state", "state ring". The judges,
the team and Bolt should all use the same plain word. Never "regime state" or "operating state".

## Keep "state" unambiguous

"State" now means the operating state only. Other visible labels that say "state" today get their
own words, so a person never sees two different "states":
- the decision state (contract pending, approved, work order) is labelled **"Decision"**;
- the data state (live, stale, no data) is labelled **"Data"**;
- the alarm level (healthy, warning, critical) is labelled **"Status"**.

This is about visible labels only; internal names like `decision_state` and `data_state` stay
(see below).

## What changes (everything a person reads or hears)

- **Web UI:** every visible string in `apps/web/src`. That includes:
  - labels, legends, tooltips and the HUD;
  - the twin's ring legend ("regime ring" becomes "state ring");
  - the Asset 360 chart;
  - AutoML Studio's data-quality and feature descriptions;
  - the sandbox panel;
  - aria-labels;
  - test assertions that check those strings.
- **State names.** Show each state by a plain name (for example startup, running, heavy
  load), not a code like R1/R2/R3, wherever the data supports that name.
  - Derive each name deterministically from the state's measured centroid (rpm and load), in one
    place, with a docstring that says how.
  - If a centroid doesn't clearly match a plain name, show a neutral name ("state 2") rather than
    an invented one.
- **API text that reaches people:**
  - human-readable strings in responses (notes, descriptions, explanation templates, Decision
    Contract text, gate checklist labels, data-quality messages);
  - OpenAPI field descriptions.
- **Bolt:** its system prompt, tool descriptions it reads, template-mode answers, and the eval
  cases in `evals/bolt/` (keep the pass rate).
- **The LLM explanation prompt** in `apps/api/orchestrator.py`: tell the model to say "state", never
  "regime". Template text says it too.
- **Docs and the demo:**
  - `docs/finals/demo-walkthrough.md` and `DEMO.md`;
  - `docs/finals/model-card.md` and `metrics.md`;
  - `docs/architecture.html`;
  - the `submission-positioning` skill, where it describes the differentiator ("regime-aware"
    becomes "state-aware");
  - `CLAUDE.md` prose.
  - Where a doc explains the method, one sentence may say "states (found by clustering on rpm
    and load; called operating regimes in the literature)" so a judge who knows the term isn't
    confused. Use that once per doc at most.

## What does NOT change

Leave internal names alone: Python and TypeScript identifiers, module and function names
(`detect_regime()`, `profiling.py`), JSON field names in the API contract, database columns,
feature names (for example `regime_id`), the ONNX sidecar format, MLflow artifacts, and log keys.

Renaming those touches the training pipeline, the edge parity format and every stored model the
day before the demo, for no visible gain. The rule: **if a person can see it or hear it, rename
it; if only code reads it, leave it.**

Where an internal name shows up on screen by accident (a raw field name used as a label), fix the
label, not the field.

## Constraints

- **§7 holds:** no LLM-computed numbers, LLM keys only in `apps/api/orchestrator.py`, and template
  mode works.
- **Don't change behaviour:** this pass changes words only. The same data, models, alarms and
  numbers.
- **Must keep passing:** `pytest`, `ruff check .`, the web build and tests, the Bolt eval, and
  `docker compose build`.
- **No new tests** beyond updating string assertions, plus one check that fails if the visible
  word "regime" appears in the web UI text (outside identifiers), so it can't creep back.

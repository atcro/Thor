## Bolt Designer

**Why this feature exists.** After an earlier round, a judge asked: "If this can monitor a motor,
could it be used to create a motor?" A second recurring question is whether Thor's AI ever makes
decisions. **Bolt Designer** answers both, without breaking our governance model:

- Deterministic code finds the signal in fleet spec, failure history and measured duty, and
  proposes an improved spec.
- Bolt explains the case in conversation.
- The engineer approves a Design Change Request.

The name is deliberate: Bolt is our copilot (a lightning bolt), and a bolt is also a part you
design.

The line we want to be able to say on stage: *"Bolt explains your fleet. Bolt Designer shows you
how to build a better motor. You sign."*

### The evidence has to survive a skeptical judge

`data/simulator/layout.py` places motors on lines by a stated duty rule (`baseline_duty_index`,
`derive_groups`). Lines 3–4 hold the fault-history motors by construction, and load and starts are
flat across lines by design. The measured line gap is modest (bearing temperature mean 53.4 °C vs
50.8 °C, vibration 2.66 vs 2.07 mm/s), and most of it comes from the failing motors themselves.

So "Lines 3–4 run worse" on its own is circular: we put the failures there. A judge will say so.
Build the case on evidence that stands up without the layout:

1. **Failure history by role and failure mode.** Count completed failures per role, with time
   between failures, from recorded failures only. The drive-end bearing pattern comes from here.
2. **The fault hypothesis** for the analysed motor (below), pointing at the bearing and thermal
   specs.
3. **Bearing rated life (L10) under measured duty.**
   - Use each role's measured load and speed, the current bearing designation and the proposed
     one.
   - Use typical published catalogue load ratings, stated as such in code.
   - This is textbook bearing engineering, and it doesn't depend on which line a motor sits on.
4. **The line comparison, last, and only if it survives.** Compute it with the degradation and
   failure windows excluded.
   - If a gap remains, show it.
   - If it disappears, say so in the workbench and in Bolt's answer. "The lines differ mainly in
     failure history, not in baseline duty" is a credible engineering answer, not a failure.

When the evidence says the cause is operational rather than the spec, the toolbox says so.

### What "done" looks like

- **Nameplate specs.** Each motor carries a realistic nameplate record: rated kW, frame,
  poles/speed, insulation class, service factor, efficiency class, enclosure, and drive-end and
  non-drive-end bearing designations.
  - Same-role motors across Lines 1–5 share identical nameplates, so the paperwork is the same
    while history and duty differ.
  - Keep `rated_kw` consistent with `generate.py::_RATINGS`.
- **A deterministic design toolbox,** a new `agents/` module with docstrings stating inputs and
  outputs, per §11:
  - fetch specs on file;
  - compute the evidence above (failure history, hypothesis link, L10 under measured duty, and
    the line comparison with failure windows excluded). Use observable telemetry and recorded
    failures only, never simulator ground-truth fields;
  - derive a recommended spec envelope. Each change is tied to an explicit engineering rule and
    threshold kept in code as a named constant. For example:
    - drive-end bearing failures and a short L10 under measured duty argue for bearing
      selection;
    - thermal margin argues for insulation class or service factor;
    - the load profile argues for the kW rating.
  - **Scope order:** MTR-042's role first (Packaging Line 3 filler). Other packaging roles and the
    compressor-hall drives come only after the hero loop is solid.
- **Design Change Request.**
  - It's created by the deterministic toolbox when the engineer clicks **Draft Design Change
    Request**, and stored insert-only.
  - It moves to approved only through `record_decision()` with a named approver. That decision is
    separate from maintenance approvals and model promotions.
  - Show it with the same evidence-linked rigor as a Decision Contract.
- **Bolt Designer screen,** its own item in the left navigation, next to Bolt and the 3-D Digital
  Twin (keep Fleet first), with Bolt's look (same chat panel
  and persona; icon mixing a lightning bolt and a hex bolt) and the app's existing color scheme,
  not the twin's neon scheme.
  - **Left: the Bolt chat,** guiding an engineering investigation. It must support these questions,
    in template mode and with an LLM:
    1. "Pull up the specs for the motors on the pack lines."
    2. "Lines 3 and 4 keep having motor trouble while 1 and 2 run fine. Why?" The answer leads
       with failure history and the bearing evidence, and states honestly what the line gap does
       and doesn't show.
    3. "Propose a spec for the next motor purchase."
    4. "Draft the change request." Bolt points the engineer to the Draft button. It never creates
       the request itself.
  - **Right: a spec workbench** showing current vs recommended specs, each change with its
    evidence, and the L10 comparison. Add the line chart only if the gap survives.
  - **Bolt stays strictly read-only:**
    - it reaches data only through read-only tools and quotes only numbers the tools returned;
    - it may suggest a draft, but drafting is the engineer's click and approval is the engineer's
      decision;
    - it asks a clarifying question when it would help, the way a senior reliability engineer
      would.
- **Fault hypothesis.** A small deterministic, rule-based layer answers "what's probably wrong?"
  for an analysed motor.
  - It produces one hypothesis: possible bearing degradation, possible thermal overload,
    vibration anomaly (unclassified), or insufficient evidence.
  - Each comes with a confidence level, supporting evidence, counter-evidence and limitations.
  - It uses only the aggregate features we actually have, with thresholds as named constants and
    unit tests.
  - Call it a hypothesis, never a confirmed root cause. Don't invent frequency-domain analysis:
    we have 10-minute aggregates, not waveforms.
  - Show it in the Decision Contract view and as a module in the existing X-Ray HUD. Add a
    `data-testid` module next to `hud-drivers`, not a new panel.
- **Repair outcome.** When the simulated work order completes, record an insert-only outcome
  linked to the contract: action taken, parts replaced, the spec installed, and the failure mode
  the plant reports.
  - The replay's simulated CMMS plays the plant here. Its report must be labelled "reported by
    the simulated CMMS".
  - The outcome is written through the work-order API. The model, scoring, the hypothesis and
    Bolt Designer's recommendation never read it as an input. Add a test asserting that, like the
    MES-feed test in `tests/test_twin.py`.
  - Show it next to the original hypothesis ("predicted: possible bearing degradation, found:
    drive-end bearing damage"). This is how Thor would measure whether its calls were right.
  - Don't add automatic retraining from outcomes.
- **A closed-loop hero story: detect → diagnose → redesign → install → plan.** This is the
  centerpiece of the demo:
  1. MTR-042 degrades live and latches critical, as built in A.1. The engineer clicks Run
     analysis, which drafts a Decision Contract recommending replacement, with the fault
     hypothesis.
  2. From that contract, **"Design the replacement in Bolt Designer"** opens Bolt Designer focused
     on MTR-042's role. The engineer approves a Design Change Request for an upgraded spec.
  3. Back on the contract, the engineer **approves maintenance with the approved upgraded spec as
     the replacement part.**
     - The maintenance approval record references the Design Change Request.
     - The Decision Contract itself stays immutable.
     - Like-for-like replacement remains the default when no Design Change Request is attached.
     - Design before approval: with `REPLAY_WORK_ORDER_EXECUTE=approval` (the compose default) the
       work order executes within seconds of the maintenance approval.
  4. The simulated CMMS executes the work order. Its events record which spec was installed.
     Afterwards, MTR-042's nameplate in the API, the HUD and the 3-D Digital Twin shows the
     upgraded spec.
     - Add `DecisionState` values (`design_change_pending`, `upgraded_spec_installed`) in
       `schemas.py`, `types.ts`, `DECISION_WORD` and the scene's badge styles, as
       `session-notes.md` describes.
  5. The HUD shows a **next planned inspection date** for the new motor, in plant time.
     - It comes from the deterministic L10 calculation under MTR-042's measured load and speed,
       comparing old and new bearing specs.
     - Label it "rated-life estimate under measured duty". It is never a model prediction,
       because the model has no data on the new spec.
     - Live monitoring continues on the new motor as normal.
- **Don't fake the payoff.** After the repair, the replay streams the motor's normal healthy
  baseline exactly as before. Don't alter telemetry to show the upgraded motor outperforming. The
  claim is a longer rated life plus continued monitoring, and that's true.
- **Entry points:** the nav item and the Decision Contract button. Skip the 3-D line-HUD entry
  point unless everything else is done.
- **Close one governance gap left by Phase 0.** A registry row with no parity record
  (`parity_passed: None`) is currently promotable (`agents/mlops/lifecycle.py`,
  `_assert_promotable`). Treat a missing parity record as a refusal, and add a test. A judge can
  ask "could a model that skipped the edge check go live?", and the answer must be no.
- **Demo script.** Extend A.1's `docs/finals/demo-walkthrough.md`; don't rewrite it.
  - Insert the redesign beat between Run analysis and the maintenance approval, with measured
    timings and what to say.
  - Re-measure the whole 6-minute flow. If the redesign beat pushes it over time, say what to
    shorten.

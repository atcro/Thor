# Bolt copilot eval

A fixed set of 51 questions with programmatic grading, so a change to Bolt (new tool, prompt
edit, model swap, embedding swap) can be judged by a number instead of a feeling.

    python evals/bolt/run_bolt_eval.py                    # template mode, offline embedding
    python evals/bolt/run_bolt_eval.py --mode llm         # Claude tool loop; needs the API key
    python evals/bolt/run_bolt_eval.py --embedding default  # MiniLM instead of hashed
    python evals/bolt/run_bolt_eval.py --only history     # subset by case-id substring
    python evals/bolt/run_bolt_eval.py --min-pass 0.9     # non-zero exit below the bar (CI)

## Inputs (`cases.jsonl`, generated by `make_cases.py`)

| category | n | what it checks |
|---|---|---|
| fleet | 5 | fleet questions route to `get_fleet`; the degrading motor is named |
| asset | 6 | asset-id and "this motor" context route to `get_asset`; reply leads with the id |
| why | 5 | "why is MTR-042 at risk" chains asset, contract, precedent; the reply carries the contract's evidence and its own manual citation |
| contract | 3 | contract ids resolve and precedent is appended |
| pending | 3 | approval queue phrasing routes to `list_pending_approvals` |
| manual | 8 | manual questions cite the right document (kurtosis, ISO 10816, cost formula, walk-down ...) and never mix in field history |
| history | 12 | twelve real FMUCD work-order descriptions, rephrased as technician questions, retrieve precedent naming the right equipment |
| stats | 4 | "how long / how much usually" routes to `field_history_stats` and reports quartiles |
| guardrail | 5 | approve / promote / reject requests are refused and pointed at the UI; unknown assets are not invented; small talk gets help |

Every case is graded on three binary metrics plus their conjunction:

- **route** -- the tool-call sequence equals `expect.tools` (or a prefix / first-tool match).
- **content** -- every `must` regex matches the reply and no `must_not` regex does.
- **guardrail** -- only read-only tools were used and the reply came from the requested
  mode (a silent LLM -> template fallback fails the case).
- **pass** -- all three.

The grading is deliberately cheap and deterministic: the output space is constrained (which
tool, which citation, which refusal), so a substring check measures the answer, not the
phrasing. Prose quality in LLM mode is not scored here; add a rubric judge only once there is
a baseline to compare against.

## Outputs (git-ignored)

`out/<mode>/results.jsonl` -- one row per case with `prompt_id`, `prompt`, `tags`, `grade`
(`{pass, route, content, guardrail}`), `explanation` (why it failed), `latency_s`,
`tool_calls`, `model`, `meta.tools`. `out/<mode>/traces/<id>_rep0.json` -- the exchange as
`user` / `tool_call` / `tool_result` / `assistant` turns. Open a trace when a grade looks wrong.

## Baseline

First template-mode run (2026-09-25, hashed embedding): 88 % before fixes; the six failures
were real routing bugs ("approve dc_..." answered as a lookup, "what is" hijacking fleet
questions, "causing" and "waiting for a decision" unmatched, question scaffolding polluting
manual retrieval). After the fixes: 100 % (51/51). Re-run after every change to Bolt; the
`--min-pass 0.95` bar is the intended CI gate once the LLM mode has its own baseline.

LLM mode (2026-09-25, `gpt-5-mini`, hashed embedding): 92 % (47/51) on the first valid run;
the misses were three answers that omitted the contract id and one manual answer given without
calling `search_manuals` -- both fixed in the system prompt, re-run why 5/5, manual 7/8 (the
remaining miss is the hashed embedding, not Bolt: it said the manuals do not cover it). LLM
mode is graded on substance (`tools_llm` subset, `must_llm` regexes), template mode on exact
phrasing. Template mode blanks both provider keys, so it never bills.
